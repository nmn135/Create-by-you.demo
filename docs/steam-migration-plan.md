# Steam 迁移方案

> 从网页版（Three.js）迁移到 Steam 独立游戏的完整路径。结论：**无需停止当前工作**，核心逻辑 100% 可复用。

## 一、核心认知

当前资产分为两层：

| 层 | 内容 | 可复用度 | 说明 |
|----|------|:---:|------|
| **游戏核心** | 状态机、AI 管线、剧情、角色、失言公式、关系网 | 100% | 与渲染引擎无关 |
| **渲染层** | Three.js 场景、对话 UI、3D 模型 | 需替换/打包 | 最易更换 |

**现在验证的是"说话改变世界"机制**——机制是否好玩与引擎无关。验证通过才值得迁移。

## 二、三条迁移路径

### 路径 A：Electron/Tauri 打包（推荐，最快）

| 项 | 说明 |
|----|------|
| 难度 | ⭐ 低 |
| 改代码量 | ~5% |
| 原理 | 用 Chromium 壳包住现有 HTML，Python 服务器作为子进程 |
| 工期 | 1-2 周 |
| 优点 | 最快上架、保留全部现有代码、社区成熟 |
| 缺点 | 不是"原生"引擎，文件体积较大（~200MB） |

**实现要点：**
- Electron 主进程启动时 spawn `python server.py` 作为本地后端
- 前端 `API_BASE` 从 `http://localhost:8080` 改为相对地址或环境变量
- 打包时用 PyInstaller 把 Python 打成 exe，或用 `node-pty` 管理子进程

### 路径 B：Unity 重写（最大投入，画面上限最高）

| 项 | 说明 |
|----|------|
| 难度 | ⭐⭐⭐ 中 |
| 改代码量 | 渲染层 ~40% 重写 |
| 工期 | 2-3 个月 |
| 优点 | 原生 3D 引擎、光照/物理/性能上限高、资产生态成熟 |
| 缺点 | 状态机需从 Python 转 C#，UI 全部重做 |

**实现要点：**
- 状态机翻译成 C#（纯逻辑，翻译机械）
- AI 管线用 C# HttpClient 调 DeepSeek API（不改）
- 对话数据从 Python 导出 JSON，Unity 读取
- 3D 场景用 Unity 重搭，Mixamo 模型可直接导入

### 路径 C：Godot 迁移（开源平衡方案）

| 项 | 说明 |
|----|------|
| 难度 | ⭐⭐ 中低 |
| 改代码量 | ~30% |
| 工期 | 1-2 个月 |
| 优点 | 开源免费、轻量、GDScript 上手快、3D 足够用 |
| 缺点 | 生态和资产市场不如 Unity |

## 三、现在就该做的 3 件事（零成本铺路）

1. **状态机保持纯逻辑**——不碰 DOM/Three.js（现在已是，持续保持）
2. **AI 管线独立封装**——已是独立模块，换引擎直接 import/翻译
3. **对话数据 JSON 化**——将来从 `game_data.py` 导出 JSON，任何引擎可读

## 四、上 Steam 的额外考虑

| 事项 | 说明 |
|------|------|
| **DeepSeek API** | 需联网；注意涨价风险（2026-08 官宣将大幅上调）与商业授权条款 |
| **Steamworks** | 成就/云存档/退款——平台层，上架前加 |
| **Mixamo 资产** | 免费但 Adobe 许可，商业游戏需确认 |
| **本地化** | 目前纯中文，上 Steam 建议加英文 |
| **DRM** | Steam 自带，无需额外 |
| **C#/Python 混合** | 若选 Electron，Python 打包成 exe 需考虑体积 |

## 五、推荐路线图

```
现在 → 网页版验证玩法（进行中）
   ↓ 验证通过
1-2周 → Electron 打包上 Steam 抢先版（验证市场）
   ↓ 有收入/反馈
2-3月 → 评估是否 Unity 重写提升画面
```

## 六、成本对比

| 路径 | 人力成本 | 额外依赖 |
|------|---------|---------|
| Electron | 低（1-2周） | 无 |
| Godot | 中（1-2月） | 无 |
| Unity | 高（2-3月） | Unity 订阅（个人版免费） |
